3. SYSTEM ARCHITECTURE & DESIGN PATTERNS
--------------------------------------------------------------------------------
Architectural Pattern: Decoupled MVVM (Model-View-ViewModel) + Repository Pattern + Reactive Riverpod Providers.

Layers Blueprint:
  1. Presentation Layer (Views / Widgets):
     - Located in `lib/features/`.
     - Zero direct data mutation. Widgets watch Riverpod providers (`ref.watch`) and emit actions (`ref.read`).
     - Fully responsive UI supporting Mobile, Tablet, and Desktop layouts via `ResponsiveLayoutShell`.

  2. State Management Layer (Riverpod ViewModels):
     - Reactive, compile-time safe state management (`flutter_riverpod: ^2.6.1`).
     - Family providers parameterize dynamic streams (e.g. `providerServicesProvider(providerId)`, `userBookingsProvider`).
     - Automatic caching, invalidation, and state propagation across widgets.

  3. Repository & Data Sourcing Layer:
     - Abstract Interfaces (`CategoryRepository`, `ProviderRepository`, `BookingRepository`, `AuthRepository`, `MessageRepository`).
     - Real-time Hybrid Implementation: Tries Firebase RTDB / REST Backend first; falls back gracefully to Hive offline storage and local JSON seeds.
     - Offline Sync Queue: Unsent offline actions are automatically queued in Hive and synced when internet connectivity returns.

6. BACKEND SERVER BLUEPRINT (NODE.JS / EXPRESS / BIGQUERY)
--------------------------------------------------------------------------------
Server File: `server/index.js`
Runtime Environment: Node.js (Port 5000 by default)
Key Technologies: Express.js, CORS, Body-Parser, Firebase Admin SDK, Google BigQuery.

Server Startup Logic:
  1. Loads regional Firebase RTDB instance: `https://meetly-fea92-default-rtdb.asia-southeast1.firebasedatabase.app`
  2. Initializes Firebase Admin SDK with `service-account.json` or fallback credentials.
  3. Pre-seeds local file databases (`settings.json`, `categories.json`, `providers.json`, `banners.json`).
  4. Publishes active server IP/URL to Firebase RTDB node `/server_url`.
  5. Syncs initial JSON state to Firebase RTDB nodes `/settings`, `/categories`, `/providers`, `/banners`.

BigQuery Telemetry Integration (`server/bigquery_service.js`):
  • Captures user navigation events, category clicks, and booking completions.
  • Generates analytics summaries (`/api/analytics/overview`, `/api/analytics/categories`).

7. DATABASE & PERSISTENCE ARCHITECTURE
--------------------------------------------------------------------------------
1. Primary Database (Cloud Realtime):
   - Engine: Firebase Realtime Database (Asia-Southeast1 Regional Cluster)
   - Database URL: `https://meetly-fea92-default-rtdb.asia-southeast1.firebasedatabase.app`
   - Nodes:
       `/server_url` : Active backend server base URL
       `/settings`   : Dynamic app banners, promo titles, and discounts
       `/categories` : Platform service category array
       `/providers`  : Verified service provider catalog
       `/banners`    : Promotional banner sliders
       `/bookings`   : Real-time user job bookings
       `/messages`   : Real-time user messaging threads

2. Local Client Storage (Offline-First Engine):
   - Engine: Hive & SharedPreferences (`lib/core/database/local_database.dart`)
   - Function: Instant cached reads, offline write queues, persistent session tokens.
   - Sync Mechanism: Automatically replays pending offline actions upon network re-establishment.

3. Server Local Storage (Fallback Persistence):
   - Location: `server/*.json` (`settings.json`, `categories.json`, `providers.json`, `banners.json`)
   - Function: Resilient fallback dataset if network connection to cloud RTDB is interrupted.

10. END-TO-END OPERATIONAL FLOWS & STATE SYNCHRONIZATION
--------------------------------------------------------------------------------
1. Authentication & Onboarding Flow:
   Customer/Provider opens app -> `SplashScreen` checks session -> If new user: `OnboardingScreen` -> `LoginScreen` / `RegisterScreen` -> Firebase Auth authenticates credential -> Fetch user profile from database -> Redirect to `/home` (Customer), `/provider/dashboard` (Provider), or `/admin/dashboard` (Admin).

2. Booking Lifecycle Flow:
   Customer selects Provider & Service -> Navigates to `/booking/create` -> Selects date, time slot, enters address & notes -> Confirms booking -> New `Booking` item written to Firebase RTDB `/bookings` & local Hive database -> State invalidated via `userBookingsProvider` -> Provider notified immediately -> Provider accepts job -> Status changes to `confirmed` -> Service delivered -> Status changes to `completed` -> Customer prompted for `Review`.

3. Real-Time Messaging Flow:
   User taps "Chat" on provider profile -> Opens `/messages/:id` -> Typing message executes `sendMessage()` -> Appends `ChatMessage` to RTDB thread -> Recipient app receives real-time snapshot listener update -> Speech bubble rendered reactively via Riverpod provider.

4. Offline-First Queue Sync Flow:
   Device loses internet -> Customer creates category/booking/profile update -> Local database saves item immediately to Hive & pushes command to `pendingQueue` -> App UI reflects change without blocking -> Internet restored -> `syncPendingQueue()` iterates queued requests, pushes to Firebase RTDB, and clears queue.
